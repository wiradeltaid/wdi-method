## Общая панорама: Разработка на базе ИИ (AiDD) vs. Спекулятивное кодирование (Vibe Coding)

Интуитивное кодирование без четких спецификаций («Vibe Coding») неизбежно терпит неудачу в долгосрочных производственных системах: ИИ-агенты кодирования теряют контекст, галлюцинируют завершение задач и размывают границы требований. WDI Method устанавливает дисциплинированную **инженерию на базе ИИ (Ai-Driven Development - AiDD)** с помощью трехуровневой архитектурной триады:

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ 1. Намерение и продуктовая стратегия: BMad Method                       │
│    Выявление проблем пользователей, составление Product Brief и архит.  │
├─────────────────────────────────────────────────────────────────────────┤
│ 2. Проверяемый слой верификации: WDI Method (SSOT)                      │
│    Управление 5 контрольными точками, связывание Цель → FR → UC → Задачи│
│    запуск валидаторов отклонений и координация автономных циклов        │
├─────────────────────────────────────────────────────────────────────────┤
│ 3. Декомпозиция и реализация: Движки навыков (mattpocock/skills)        │
│    to-spec и to-tickets декомпозируют задачи; implement выполняет TDD   │
└─────────────────────────────────────────────────────────────────────────┘
```

### Золотой инвариант: Документы следуют за кодом (Documents Follow Code)
Документы представляют собой фиксацию уже выполненной работы. Если запись о принятом решении или строка требования противоречит коду, **код имеет приоритет, а документ корректируется**. Код никогда не переписывается в угоду устаревшей документации. Документ, который просто отстает от кода, находится в нормальном рабочем состоянии и никогда не блокирует релиз, если только он не содержит критически дезинформирующих сведений.

## Быстрый старт за 10 минут

Установите WDI Method в репозиторий вашего продукта за три последовательных шага. Все диалоговые подсказки предлагают разумные значения по умолчанию; нажатие <kbd>Enter</kbd> подтверждает выбор.

### Шаг 1: Установка BMad Method
Устанавливает движок обнаружения и структурирования в репозиторий:
```bash
cd /путь/к/вашему/репозиторию
npx bmad-method install
```

### Шаг 2: Добавление шести движков задач
Установите исполнительные движки непосредственно в репозиторий (выберите "copy" или "symlink"):
```bash
npx skills@latest add mattpocock/skills
```
*Выберите все шесть движков, используемых методом:* `to-spec`, `to-tickets`, `implement`, `tdd`, `code-review`, и `domain-modeling`.

> **Почему плагина Claude Code недостаточно:** Движки в апстриме поставляются с флагом `disable-model-invocation: true`. WDI Method автоматически снимает это ограничение в локальных копиях, чтобы автономные циклы могли выполняться без ручных подтверждений. Пользовательский плагин нельзя скорректировать на уровне репозитория.

### Шаг 3: Установка WDI Method
Запустите интерактивный установщик и настройте навыки на ваших агентных платформах (Claude Code, Cursor и др.):
```bash
npx wdi-method
```
*(Для автоматизированных CI-сред: `npx wdi-method install --yes --agents claude --product "Ваш Продукт"`)*

### Ваша первая команда: `/wdi-help`
Внутри вашего ИИ-агента кодирования выполните:
```text
/wdi-help
```
`wdi-help` обращается к `.control/registry/` и сообщает точную контрольную точку, на которой находится проект, не делая предположений на основе истории чата.

## Три варианта рабочего процесса

WDI Method адаптирует уровень регламентации к масштабу и рискам задачи:

### Вариант A: Управляемый трек поставки (Новые инициативы и G1–G5)
Для новых продуктов, крупных инициатив и масштабных изменений архитектуры. Человек изучает **одну отрендеренную страницу** на каждой контрольной точке и принимает решение: *утвердить или доработать*.

| Контрольная точка | Решаемый вопрос | Вызываемый навык | Рендеринг для проверки | Решение владельца |
|---|---|---|---|---|
| **G1 — Проблема** | Реальна ли проблема и заслуживает ли она работы? | `/wdi-problem` | `.what-rendered/_product-brief/brief.md` | Утвердить формулировку проблемы |
| **G2 — Продукт** | Что мы создаем и как ощущается интерфейс? | `/wdi-product`<br>`/wdi-ux` | `.what-rendered/_prd/<slug>/prd.md` | Утвердить функциональные требования (FR) |
| **G3 — Чертеж** | Сохраняет ли устойчивость вся архитектура? *(1 раз/репо)* | `/wdi-blueprint` | `.how-rendered/blueprint.md` | Утвердить архитектурный каркас |
| **G4 — Компонент** | Как устроен этот компонент? *(Пропуск в режиме catalog)* | `/wdi-component` | `.how-rendered/<pc>/SDD-<pc>.md` | Утвердить дизайн ПО (SDD) |
| **G5 — Сборка** | Реализована ли задача и доказано ли качество? *(На spec)* | `/wdi-build` | Вывод тест-раннера (Red → Green) | Принять объединенный код |

#### Два регулятора, которые никогда не смешиваются: Mode vs. Risk
- **`mode`** определяет состав контрольных точек (`catalog` пропускает G4; `guarded` и `deep` требуют детального SDD).
- **`risk_accepted`** задает требуемую глубину подтверждения проверки (`low`, `medium`, `high`). Их объединение в один переключатель либо перегружает простые компоненты бюрократией, либо пропускает рискованные изменения без проверки.

## Инварианты из реальной практики и операционные знания

Проверенные правила, выявленные в ходе боевой эксплуатации мультиагентных систем:

1. **Фиксация роли Builder на координаторе (`builder: coordinator`):** В `wdi-daily-autopilot` координирующая сессия пишет код напрямую через TDD-циклы. Делегирование написания кода субагентам приводит к галлюцинациям в отчетах о прохождении тестов.
2. **Независимые консультативные ревьюеры:** Внешние рецензенты (например, Terra) работают исключительно в режиме чтения (`--trust-tools=fs_read` / `--mode plan`). Они анализируют граничные случаи, не изменяя код. Принцип единственного автора (*Single-Writer*) строго соблюдается.
3. **Предотвращение блокировки файлов в Windows (Process Gating):** В Windows фоновые процессы удерживают дескрипторы открытыми, вызывая ошибки `Access is denied (Exit code 5/32)` при компиляции или очистке worktree. `wdi-daily-what-to-test` завершает остаточные процессы перед сборкой.
4. **Обязательная изоляция в Git Worktree:** Автономные циклы кодирования (`wdi-autopilot`) **должны выполняться в изолированном git worktree** (`autopilot/<mandate-id>`). Никогда не запускайте автономные циклы в основном рабочем дереве.
5. **Единый запуск Cloud CI на каждый PR:** Автономные циклы фиксируют коммиты локально по каждой задаче. Запуск облачного CI на каждой итерации быстро исчерпывает месячные лимиты. Локальные тесты обеспечивают авторитетное подтверждение; Cloud CI запускается **один раз**, когда PR готов к ревью.
6. **Гигиена временных артефактов:** Курсоры смоук-тестов и манифесты сред выполнения локальны для машины. Убедитесь, что `.work/smoke/` внесен в `.gitignore`.

## Структура репозитория и инварианты

```text
.constitution/
  method/            Движок метода — перезаписывается при каждом обновлении; не редактировать
  project/           Собственные правила проекта и ридеры инвентаря — сохраняются при обновлениях
.control/
  registry/          Единый источник истины (SSOT): goals.yaml · specs.yaml · components.yaml
  decisions/         Принятые решения и мандаты владельца (DEC-*.md)
  memlog/            Журналы аудита, фиксирующие решения автономных циклов
  test-targets/      Шаблоны физического тестирования (desktop.md, web.md, mobile.md)
.scratch/            Рабочие пространства активных спецификаций (SPEC-*.md и задачи)
.archive/            Архивированные исторические спецификации с сохраненными связями RTM
.what/ & .how/       Рабочие документы корпуса (PRD, SRS, Blueprint, SDD)
.what-rendered/      Сгенерированные человеком читаемые артефакты (validate.py / wdi-report)
```

## Вклад в проект и архитектурные основы

Любой вклад в WDI Method должен отвечать на один вопрос: **делает ли это слой верификации более надежным или просто более громоздким?**

### Фикстурный корпус и локальная верификация
Все изменения валидаторов и фреймворка проверяются на внутреннем тестовом корпусе (`tests/fixture/`). Перед созданием pull request запустите полный набор тестов:
```bash
npm test
```

### Правило публичного универсального пакета
WDI Method публикуется в открытом реестре npm. Он никогда не должен содержать имена частных клиентов, коммерческие идентификаторы продуктов, внутренние сетевые учетные данные или абсолютные пути к файлам.
